## 2. 四层分析模型

### 2.1 分析层次总览

| 层次 | 核心问题 | 关键技术 | 典型场景 | 复杂度 |
|------|---------|---------|---------|--------|
| **描述性分析** | 发生了什么？ | 聚合统计、KPI报表、Dashboard | 日报/周报、销售汇总 | 入门 |
| **诊断性分析** | 为什么发生？ | Drill-down、相关性分析、根因分析 | 流量突降归因、异常排查 | 中级 |
| **预测性分析** | 将来可能发生什么？ | 回归、时间序列(ARIMA)、ML模型 | 需求预测、流失预警、风险评估 | 高级 |
| **规范性分析** | 应该怎么做？ | 优化算法、仿真模拟、推荐引擎 | 动态定价、资源调度、个性化推荐 | 专家 |

> **实战原则**：大多数组织同时使用四种分析的组合。不要跳级——先做好描述性分析，再做诊断性，逐层递进。规范性分析不仅预测未来还推荐具体行动。

### 2.2 每层分析的标准流程

**描述性分析 SOP**：
1. 明确分析目标（谁要看？为什么看？）
2. 定义 KPI 和度量标准
3. 数据获取与清洗
4. 聚合计算（按维度/时间/分组）
5. Dashboard 搭建与交付
6. 设置数据监控告警

**诊断性分析 SOP**：
1. 识别异常（与基线/预期/同期对比）
2. 维度拆解（按渠道/地区/产品/用户群）
3. 假设生成（列出可能原因）
4. 逐项验证（数据验证每个假设）
5. 根因定位（找到最可能的解释）
6. 修复建议与验证

## 3. 数据清洗与预处理

### 3.1 数据质量五维度

| 维度 | 定义 | 检查方法 | 常见问题 |
|------|------|---------|---------|
| **准确性** | 数据值是否正确反映现实 | 交叉验证、业务规则 | 录入错误、单位混淆 |
| **完整性** | 字段缺失率 | NULL计数、缺失模式分析 | 用户未填、系统故障 |
| **一致性** | 跨系统数据是否统一 | 跨表JOIN验证 | 命名不统一、格式差异 |
| **时效性** | 数据是否及时更新 | 时间戳检查、延迟监控 | ETL延迟、接口故障 |
| **有效性** | 是否符合预定义规则 | 正则匹配、范围检查 | 越界值、非法格式 |

### 3.2 标准清洗流程

```
数据探查(Profiling)
    → 了解分布、异常点、缺失模式
    → 工具：df.describe()、df.info()、缺失值热力图

去重(Deduplication)
    → 精确去重 + 模糊匹配去重
    → 工具：df.drop_duplicates()、record linkage

标准化(Standardization)
    → 统一格式（日期、地址、命名规范、编码）
    → 工具：str.normalize()、正则替换

验证(Validation)
    → 业务规则校验、边界检查
    → 工具：Great Expectations、Pandera

修复(Remediation)
    → 填充缺失值、纠正异常
    → 策略：删除/填充(均值中位数众数)/插值/模型预测

监控(Monitoring)
    → 持续质量检查和告警
    → 工具：dbt tests、DataDog、自定义脚本
```

### 3.3 Python 清洗代码模板

```python
import polars as pl  # 推荐，比 pandas 快 10-100x

# 读取数据
df = pl.read_csv("raw_data.csv")

# 数据探查
print(df.describe())
print(df.null_count())  # 缺失值统计

# 清洗管道
clean_df = (
    df
    # 去重
    .unique(subset=["user_id", "date"])
    # 标准化列名
    .rename({col: col.lower().strip().replace(" ", "_") for col in df.columns})
    # 填充缺失值
    .with_columns(
        pl.col("amount").fill_null(0),
        pl.col("category").fill_null("unknown"),
        pl.col("date").fill_null(pl.lit("1970-01-01"))
    )
    # 过滤异常值
    .filter(pl.col("amount").is_between(0, 1_000_000))
    # 类型转换
    .with_columns(
        pl.col("date").str.to_date("%Y-%m-%d"),
        pl.col("amount").cast(pl.Float64)
    )
)
```

> **Gotcha**：Polars 和 Pandas API 差异大——Polars 不支持 `.loc[]` / `.iloc[]`，惰性 API `.lazy()` 和立即 API `.collect()` 混用容易困惑。大型生态（scikit-learn）仍以 Pandas DataFrame 为接口标准。

## 4. 数据可视化设计原则

### 4.1 Tufte 经典原则

| 原则 | 说明 | 实践 |
|------|------|------|
| **数据墨水比** | 图表中大部分视觉元素应代表实际数据 | 移除多余网格线、阴影、3D效果、背景图案 |
| **图形完整性** | 视觉表示应与数据数量关系成正比 | 坐标轴从零开始、避免截断Y轴 |
| **谎言因子** | 数据表现大小与实际大小的比率应接近1 | 不用面积图夸大差异 |
| **数据变异优先** | 展示数据本身的变异，而非设计变异 | 用简洁设计让数据说话 |
| **标注清晰** | 详细标注，标注数据本身而非装饰 | 直接标注数值而非图例 |
| **多层信息** | 在有限空间中嵌入多层信息 | 使用微型图表(Sparklines)、数据注脚 |

> "Above all else show the data." — Edward Tufte

### 4.2 图表选型决策树

```
你要表达什么关系？
├── 比较（谁多谁少？）
│   ├── 分类比较 → 柱状图（Bar Chart）
│   ├── 时间比较 → 折线图（Line Chart）
│   └── 多维比较 → 雷达图 / 热力图
├── 趋势（怎么变化？）
│   ├── 连续时间趋势 → 折线图
│   ├── 周期性趋势 → 日历热力图
│   └── 多系列趋势 → 多折线图（≤5条）
├── 构成（各占多少？）
│   ├── 静态构成 → 饼图（≤5类）/ 堆叠柱状图
│   ├── 动态构成 → 堆叠面积图
│   └── 层级构成 → 瀑布图 / 树状图
├── 分布（集中在哪？）
│   ├── 单变量分布 → 直方图 / 箱线图
│   ├── 双变量分布 → 散点图 / 密度图
│   └── 多变量分布 → 散点矩阵 / 热力图
├── 相关（有关系吗？）
│   ├── 线性相关 → 散点图 + 趋势线
│   ├── 非线性相关 → 散点图（可能需要变换）
│   └── 多变量相关 → 相关系数热力图
└── 地理（空间分布）
    ├── 空间分布 → 地图（Choropleth）
    ├── 流向关系 → 飞线图
    └── 密度分布 → 热力地图
```

### 4.3 可视化 7 条铁律

1. **先选图表类型再谈美化**——匹配数据关系是第一位
2. **每张图只传达一个核心信息**——不要让受众自己去"解读"
3. **颜色做有意义编码，不做装饰**——同类同色、异类异色
4. **标注数据而非图例**——直接在图表上标注数值和标签
5. **避免 3D 效果**——3D 柱状图/饼图严重扭曲数据感知
6. **使用留白而非填充创造层次**——信息密度≠视觉密度
7. **面向受众调整深度**——高管要结论，分析师要方法论

## 6. SQL 高级查询模式

### 6.1 窗口函数核心

```sql
-- 窗口函数标准语法
function_name(expression) OVER (
    PARTITION BY column      -- 分组（类似 GROUP BY，但不折叠行）
    ORDER BY column          -- 组内排序
    ROWS/RANGE frame_spec    -- 帧定义（窗口范围）
)
```

**核心函数表**：

| 函数 | 作用 | 典型场景 |
|------|------|---------|
| ROW_NUMBER() | 行号（不处理并列） | Top N 去重、分页 |
| RANK() / DENSE_RANK() | 排名（处理并列） | 绩效排名 |
| LEAD(col, n) / LAG(col, n) | 前后N行值 | 环比分析、间隔计算 |
| SUM/AVG OVER() | 累计/移动平均 | 运行总计、移动均值 |
| FIRST_VALUE / LAST_VALUE | 首尾值 | 首次/末次行为分析 |
| NTILE(n) | 分成N组 | 用户分层(高/中/低) |

### 6.2 五大经典分析模式

**1. 同期群分析(Cohort Analysis)**：
```sql
WITH cohort AS (
    SELECT
        user_id,
        DATE_TRUNC('month', first_order_date) AS cohort_month
    FROM users
),
retention AS (
    SELECT
        c.cohort_month,
        COUNT(DISTINCT c.user_id) AS cohort_size,
        COUNT(DISTINCT CASE WHEN DATE_TRUNC('month', o.order_date) = c.cohort_month + INTERVAL '1 month'
            THEN c.user_id END) AS m1_retained
    FROM cohort c
    LEFT JOIN orders o ON c.user_id = o.user_id
    GROUP BY 1
)
SELECT
    cohort_month,
    cohort_size,
    m1_retained,
    ROUND(100.0 * m1_retained / cohort_size, 1) AS m1_rate
FROM retention
ORDER BY cohort_month;
```

**2. 漏斗分析(Funnel Analysis)**：
```sql
SELECT
    COUNT(DISTINCT CASE WHEN step = 'view' THEN user_id END) AS views,
    COUNT(DISTINCT CASE WHEN step = 'cart' THEN user_id END) AS carts,
    COUNT(DISTINCT CASE WHEN step = 'pay' THEN user_id END) AS payments,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN step = 'cart' THEN user_id END) /
        NULLIF(COUNT(DISTINCT CASE WHEN step = 'view' THEN user_id END), 0), 1) AS view_to_cart,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN step = 'pay' THEN user_id END) /
        NULLIF(COUNT(DISTINCT CASE WHEN step = 'cart' THEN user_id END), 0), 1) AS cart_to_pay
FROM user_events
WHERE event_date >= '2026-01-01';
```

**3. 留存分析(Retention)**：使用 LAG 窗口函数按用户计算连续活跃天数

**4. 用户路径分析(Path Analysis)**：使用 LEAD/LAG 窗口函数追踪用户行为序列

**5. 运行总计/移动平均**：使用 SUM/AVG OVER() 计算累计值和滚动均值

### 6.3 CTE 最佳实践

```sql
-- ✅ 正确：用 CTE 替代嵌套子查询，提升可读性
WITH monthly_revenue AS (
    SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total
    FROM orders GROUP BY 1
),
monthly_growth AS (
    SELECT month, total,
           total - LAG(total) OVER (ORDER BY month) AS growth
    FROM monthly_revenue
)
SELECT * FROM monthly_growth WHERE growth > 0;

-- ❌ 错误：三层嵌套子查询——可读性极差
SELECT * FROM (
    SELECT month, total, total - (SELECT ...) FROM (
        SELECT DATE_TRUNC('month', ...) AS month, SUM(...) AS total
        FROM orders GROUP BY 1
    )
)
```

> **Gotcha**：GROUP BY 会折叠行（每组一行），OVER() 不折叠（保留每行同时计算聚合值）。这是最常见的面试考点。

## 7. 数据驱动决策框架

### 7.1 A/B 测试全流程

```
假设构建 → 指标定义 → 样本量计算 → 实验运行 → 结果分析 → 决策
   ↓           ↓            ↓            ↓           ↓        ↓
 业务洞察    核心+护栏     功效80%+     随机分组    显著性    上线/下线
             指标体系    显著性95%    SRM检查    检验
```

**关键概念**：

| 概念 | 说明 |
|------|------|
| 核心指标(Primary Metric) | 直接衡量实验目标（如转化率） |
| 护栏指标(Guardrail Metric) | 确保不损害其他方面（如跳出率） |
| SRM检查 | Sample Ratio Mismatch，确保分组比例正确 |
| 统计功效(Statistical Power) | 检测到真实效应的概率（通常≥80%） |
| 显著性水平(α) | 假阳性概率（通常≤5%） |
| 最小可检测效应(MDE) | 能可靠检测到的最小差异 |

### 7.2 频率学派 vs 贝叶斯

| 维度 | 频率学派 | 贝叶斯 |
|------|---------|--------|
| 核心指标 | p值、置信区间 | 后验概率、期望损失 |
| 决策方式 | 拒绝/不拒绝零假设 | P(Better) > 阈值即行动 |
| 样本量 | 固定预计算 | 可灵活停止 |
| 实验速度 | 基准 | 快 23-31% |
| 适用场景 | 严格科学实验 | 快速迭代产品实验 |

### 7.3 实战最佳实践

- 二元结果的最佳样本量：每组 300-500 次转化
- 永远不要在实验运行中途偷看结果做决策（频率学派）
- Group Sequential Tests (GST) 和 Always Valid Inference (AVI) 是应对持续监控的现代方法
- 先定义指标体系再跑实验——"什么都没定义"是最大失败原因

> **Gotcha**：贝叶斯 A/B 测试的先验分布错误设定是最常见的实施失败原因。建议从无信息先验(Uniform)开始，逐步累积领域知识。

## 8. 统计学核心概念

### 8.1 必掌握体系

| 概念 | 一句话解释 | 应用场景 |
|------|-----------|---------|
| **假设检验** | 用数据判断某个假设是否成立 | A/B测试、效果验证 |
| **p值** | 零假设为真时观察到当前结果的概率 | 判断结果是否显著 |
| **置信区间** | 真实值可能落入的范围 | 估计精度、效果大小 |
| **第一类错误(α)** | 假阳性——没效果却说有效 | 错误上线 |
| **第二类错误(β)** | 假阴性——有效却说没效果 | 错过机会 |
| **统计功效(1-β)** | 检测到真实效应的概率 | 样本量设计 |
| **回归分析** | 建立变量间的数学关系 | 预测、归因、趋势分析 |
| **贝叶斯定理** | 用新证据更新先验信念 | 动态决策、风险评估 |

### 8.2 回归分析选型

| 类型 | 因变量 | 适用场景 | 工具 |
|------|--------|---------|------|
| 线性回归 | 连续值 | 房价预测、销量预测 | statsmodels、sklearn |
| 逻辑回归 | 二分类 | 转化预测、流失预警 | statsmodels、sklearn |
| 多元回归 | 多特征连续值 | 多因子模型 | statsmodels |
| 正则化(Ridge/Lasso) | 防过拟合 | 高维特征、特征选择 | sklearn |

### 8.3 Gotchas 清单

- **p值 < 0.05 不等于"有实际业务意义"**——需同时看效应大小
- **多重比较问题**：跑 100 个检验，纯随机也会出 5 个"显著"——需 Bonferroni 校正或 FDR 控制
- **相关性 ≠ 因果性**——永远是。可能是混淆变量
- **过拟合**：模型训练集好、测试集差——交叉验证是标配
- **生存偏差**：只分析"活下来"的数据，忽略已淘汰的样本

## 9. 数据 Storytelling

### 9.1 情境-冲突-解决方案框架

```
┌─────────────────────────────────────────────────┐
│ 情境 (Context)                                    │
│ "我们的月活跃用户从 50 万增长到 80 万"              │
│ → 设定背景，让受众建立共同认知                        │
├─────────────────────────────────────────────────┤
│ 冲突 (Complication)                               │
│ "但付费转化率从 3.2% 下降到 1.8%，ARPU 降低 44%"    │
│ → 引发关注，制造"需要解决"的紧迫感                    │
├─────────────────────────────────────────────────┤
│ 解决方案 (Resolution)                              │
│ "通过漏斗分析发现支付页加载时间增加 2s，              │
│  优化后转化率恢复至 3.5%，预计月增收 12 万"           │
│ → 给出数据支撑的行动建议                             │
└─────────────────────────────────────────────────┘
```

### 9.2 关键原则

| 原则 | 说明 |
|------|------|
| **受众优先** | 高管要结论（1分钟），分析师要方法论，运营要可操作项 |
| **金字塔原理** | 结论先行，自上而下展开 |
| **用异常值讲故事** | 人们记不住"正常"，记住的是"不同" |
| **三要素缺一不可** | 数据 + 叙事 + 视觉 |
| **可操作性** | 每个洞察都要带"所以我们应该做什么" |

## 10. 数据仓库与数据湖

### 10.1 架构对比

| 维度 | 数据仓库 | 数据湖 | Lakehouse |
|------|---------|--------|-----------|
| **数据类型** | 结构化 | 全类型 | 全类型 |
| **Schema** | Schema-on-Write | Schema-on-Read | 两者兼顾 |
| **处理模式** | ETL | ELT | ELT + 流批一体 |
| **使用者** | 分析师/BI | 数据科学家 | 全角色 |
| **代表产品** | Snowflake/BigQuery | S3/ADLS | Databricks/Delta Lake |

### 10.2 星型 vs 雪花模型

| 模型 | 结构 | 优势 | 劣势 | 推荐 |
|------|------|------|------|------|
| **星型模型** | 事实表 + 不规范化维度表 | 查询简单、JOIN少、性能好 | 数据冗余 | 大多数场景首选 |
| **雪花模型** | 维度表进一步规范化 | 减少冗余 | JOIN复杂、查询慢 | 数据变更频繁时 |

### 10.3 ETL vs ELT

| 维度 | ETL | ELT |
|------|-----|-----|
| 流程 | Extract → Transform → Load | Extract → Load → Transform |
| 转换时机 | 加载前 | 加载后（利用目标系统算力） |
| 灵活性 | 低（需预定义Schema） | 高（原始数据先落地） |
| 趋势 | 传统方案 | **2025年主流**（云仓库弹性计算） |

### 11.2 五大支柱

```
1. 数据探查(Profiling) → 了解数据现状
2. 标准化(Standardization) → 命名规范、格式统一
3. 验证(Validation) → 业务规则校验
4. 治理(Governance) → 角色职责、权限管理
5. 度量(Measurement) → 质量KPI、持续改进
```

### 11.3 实战建议

- 脏数据喂 AI 只会得到"自信的错误"——数据质量是所有分析的基线
- 自动化清洗 + 持续监控，而非"投诉了才修"
- 用 dbt test 做数据测试、Great Expectations 做数据验证
- 建立数据字典(documentation)——让每个人都能理解字段含义

## 12. 2025-2026 新兴趋势

### 12.1 AI 增强分析（最核心趋势）

- Gartner 预测：到 2026 年，40% 的分析查询将使用自然语言创建
- Power BI Copilot、Tableau GPT、AI Query 正在降低分析门槛
- **关键前提**：语义层(Semantic Layer) + 业务上下文 = LLM 查询准确率从 20% → 95%+

### 12.2 数据网格(Data Mesh)

- 从集中式数据仓库转向去中心化——领域团队拥有并服务于自己的数据产品
- 四大原则：面向域的所有权、数据即产品、自助式基础设施、联邦计算治理
- 适合：数据量爆炸 + 敏捷需求高的中大型组织

### 12.3 实时分析(Real-Time Analytics)

- 从"事后分析"转向"实时响应"——每一秒都可能影响收入或风险
- 混合架构：流式处理(Kafka/Flink) + 批量处理结合

### 12.4 趋势决策矩阵

| 组织规模 | 数据成熟度 | 推荐架构 |
|---------|-----------|---------|
| 初创/小团队 | 低 | ELT + Metabase + Polars |
| 中型企业 | 中 | Lakehouse + Superset + dbt + 语义层 |
| 大型企业 | 高 | Data Mesh + Lakehouse + AI增强分析 |

## 13. 场景脚本

### 场景一：初创公司数据体系建设

**用户**："我们是个 10 人 SaaS 团队，想建立数据分析能力，从零开始"

**执行步骤**：
1. **定义核心指标**：北极星指标 + 3-5 个关键 KPI（收入、DAU、转化率、流失率）
2. **选择工具链**：Polars(数据处理) + Metabase(BI) + dbt(转换) + PostgreSQL(存储)
3. **搭建数据管道**：事件埋点 → 数据收集 → ETL → 仓库 → Dashboard
4. **建立数据质量**：dbt test 做自动化验证 + 每日数据质量检查
5. **设计核心报表**：收入趋势、用户漏斗、留存曲线、功能使用热度
6. **迭代优化**：根据业务反馈调整指标和报表

### 场景二：A/B 测试全流程

**用户**："我们要测试新落地页是否提高注册转化率"

**执行步骤**：
1. **假设**：新落地页将注册转化率从 5% 提升到 6%（相对提升 20%）
2. **指标**：核心=注册转化率，护栏=页面加载时间、跳出率
3. **样本量**：每组需 ~4,500 访问者（功效 80%，显著性 5%）
4. **运行周期**：约 2 周（基于当前流量）
5. **SRM 检查**：确认 50/50 分流无偏差
6. **结果分析**：计算 p 值和置信区间
7. **决策**：统计显著 + 护栏无损 → 全量上线

### 场景三：数据异常排查

**用户**："今天 DAU 突降 30%，需要快速找到原因"

**执行步骤**：
1. **确认数据质量**：先排除数据管道故障、埋点丢失
2. **维度拆解**：按平台(iOS/Android/Web)、地区、渠道、版本拆解
3. **时间定位**：下降从哪个时间点开始？是否与发布/事件关联？
4. **假设验证**：
   - 新版本 Bug？→ 对比新版本 vs 旧版本用户
   - 服务器故障？→ 检查错误日志和响应时间
   - 外部事件？→ 检查竞品动态、节假日、天气
5. **根因确认**：定位到最可能原因
6. **修复与复盘**：紧急修复 + 建立监控告警防止复发

## 15. 风险提示

| 风险 | 说明 | 应对 |
|------|------|------|
| 数据质量陷阱 | 脏数据导致"自信的错误"结论 | 建立数据质量基线和持续监控 |
| 相关性误导 | 相关≠因果，容易做出错误归因 | 控制变量、A/B测试验证 |
| p值滥用 | p<0.05≠有业务意义 | 同时看效应大小和置信区间 |
| 过拟合 | 模型训练好但泛化差 | 交叉验证、正则化 |
| 仪表盘膨胀 | 越做越多，没人看 | 定期清理、聚焦核心指标 |
| AI幻觉查询 | LLM无语义层生成错误SQL | 建立语义层再做AI增强分析 |
| 选择性报告 | 只展示"好看"的数据 | 主动展示反向证据 |
