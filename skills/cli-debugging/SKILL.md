# CLI 与代理环境故障排查工作环境

> 基于《Claudian 会话卡死排查记录 (2026-07-12)》封装的可复用技能。
> 本技能覆盖 CLI/Node.js 工具在代理环境下的网络故障排查方法论，包括环境变量继承问题、系统代理 vs 环境变量代理的差异、对照实验定位法、排查弯路分析与修复策略。

---

## 1. 任务边界

**做**
- 提供 CLI/Node.js 工具"连不上 API 但浏览器正常"类故障的标准化排查流程
- 解释 macOS/Windows/Linux 环境变量继承机制的差异与陷阱
- 提供 Node.js 代理行为的核心知识：只认环境变量，不读系统代理
- 指导对照实验定位法：有 X vs 无 X 的二元对照
- 提供进程环境变量检查、TCP 连接检查的系统命令速查
- 指导 Obsidian Claudian 插件的代理配置持久化方案
- 分析排查中被表象误导的典型模式与应对策略
- 提供 TUN 模式透明代理的局限性和不可靠场景
- 指导"之前能用现在不能用但没改配置"类故障的根因定位方法
- 提供同类故障的速查决策树

**不做**
- 不提供具体代理软件（FlClash/V2Ray/Clash 等）的安装和配置指导
- 不涉及 VPN、SSH 隧道等其他网络代理方案
- 不处理 DNS 解析、防火墙规则等网络层问题
- 不提供 Claude API 密钥管理或账户问题排查
- 不涉及 Obsidian 插件开发或 Claudian 源码修改

## 2. 核心知识点

### 2.1 关键机理：Node.js 只认环境变量

```
┌─────────────────────────────────────────────────────┐
│              代理获取方式对比                          │
├──────────────┬──────────────────┬───────────────────┤
│    应用类型   │   系统代理(scutil)  │  环境变量(env)     │
├──────────────┼──────────────────┼───────────────────┤
│ GUI 应用      │ ✅ 自动读取       │ ❌ 通常不读取      │
│ (Safari等)   │ (HTTPEnable=1)   │                   │
├──────────────┼──────────────────┼───────────────────┤
│ Node.js CLI   │ ❌ 完全无视       │ ✅ 唯一来源        │
│ (claude等)   │                  │ (http_proxy)      │
├──────────────┼──────────────────┼───────────────────┤
│ Python requests│ ❌ 不自动读      │ ✅ 读取 env        │
├──────────────┼──────────────────┼───────────────────┤
│ curl          │ ✅ 可配置        │ ✅ 优先读 env      │
└──────────────┴──────────────────┴───────────────────┘
```

**核心事实**：Claude CLI 底层是 Node.js，只读取 `http_proxy` / `https_proxy` 环境变量，**不读** macOS 系统代理设置（`scutil --proxy` 那一套 `HTTPEnable/HTTPProxy`）。这是解开全部矛盾的钥匙。

### 2.2 环境变量继承陷阱

```
┌─────────────────┐
│  从终端启动应用    │ → 继承 shell 的全部 env（包括 proxy）✅
└─────────────────┘

┌─────────────────┐
│  从 Dock/桌面启动 │ → 不继承 shell env（proxy 丢失）❌
└─────────────────┘

┌─────────────────┐
│  从 launchd 启动  │ → 依赖 launchctl setenv 配置
└─────────────────┘
```

> **关键洞察**：不是"配置变了"，而是"CLI 恰好能拿到代理"这一脆弱条件在反复重启中断了。之前 Dock 启动能用，是因为进程碰巧继承了带 proxy env 的启动环境。

### 2.3 TUN 模式的局限性

| 场景 | TUN 是否生效 | 说明 |
|------|-------------|------|
| 普通网络请求 | ✅ 大部分生效 | 通过虚拟网卡 utun0-3 转发 |
| 127.0.0.1 / 本地回环 | ❌ 可能不生效 | TUN 对本地回环流量的透明代理并不可靠 |
| 某些进程 | ❌ 不保证 | 取决于进程的网络栈和 TUN 实现细节 |

> **Gotcha**：系统代理对普通 GUI App 透明生效，Node.js/CLI 却无视它；TUN 模式对 127.0.0.1 及某些进程的透明代理并不可靠。不要假设 TUN 万能。

## 3. 标准排查流程

### 3.1 四步排查法

```
Step 1: 确认故障现象
  "CLI 卡死/无响应/无网络连接"
      ↓
Step 2: 对照实验定位（核心步骤）
  有 proxy env vs 无 proxy env → 二元对照
      ↓
Step 3: 检查进程环境变量
  ps -wwE <pid>  或  Get-Process <pid> | Select-Object -ExpandProperty EnvironmentVariables
      ↓
Step 4: 检查 TCP 连接
  lsof -iTCP  或  netstat -an  → 确认是否建立 API 连接
```

### 3.2 排查命令速查

| 平台 | 命令 | 用途 |
|------|------|------|
| **macOS** | `ps -wwE <pid>` | 查看进程完整环境变量 |
| **macOS** | `lsof -iTCP` | 查看进程 TCP 连接 |
| **macOS** | `scutil --proxy` | 查看系统代理设置 |
| **macOS** | `env -u http_proxy -u https_proxy <cmd>` | 手动去掉代理变量测试 |
| **macOS** | `launchctl setenv HTTPS_PROXY http://127.0.0.1:7890` | 设置登录级全局变量 |
| **Windows** | `Get-Process <pid> \| Select-Object -ExpandProperty EnvironmentVariables` | 查看进程环境变量 |
| **Windows** | `netstat -an \| findstr 7890` | 查看到代理端口的连接 |
| **Windows** | `$env:HTTPS_PROXY="" ; <cmd>` | 去掉代理变量测试 |
| **Linux** | `cat /proc/<pid>/environ \| tr '\0' '\n' \| grep proxy` | 查看进程代理变量 |
| **Linux** | `ss -tnp \| grep 7890` | 查看代理端口连接 |

### 3.3 决定性证据对照表

| 场景 | 代理 env | 预期结果 | 如果不符合 |
|------|---------|---------|-----------|
| 终端手动跑 CLI | ✅ 有 | ✅ 正常（3秒返回） | CLI 本身有问题 |
| 从终端启动 GUI 应用 | ✅ 继承 | ✅ 正常 | 应用本身有问题 |
| 从 Dock/桌面启动 | ❌ 丢失 | ❌ 卡死（0 网络连接） | **确认是环境变量问题** |
| 手动去掉 proxy env | ❌ 无 | ❌ 复现卡死 | **确认是 proxy 导致** |

## 4. 修复方案

### 4.1 修复优先级

| 优先级 | 方案 | 影响范围 | 持久性 | 推荐度 |
|--------|------|---------|--------|--------|
| **P0** | 应用内设置写入环境变量 | 仅该应用 | 持久 | ⭐⭐⭐ 首选 |
| **P1** | launchctl setenv（macOS） | 该用户所有应用 | 持久到重启 | ⭐⭐ 全局需求时用 |
| **P2** | Shell profile 写入（.bashrc/.zshrc） | 仅终端启动的应用 | 持久 | ⭐ 仅终端场景 |

### 4.2 P0 方案：Claudian 配置示例

```json
// .claudian/claudian-settings.json
{
  "providerConfigs": {
    "claude": {
      "environmentVariables": "HTTP_PROXY=http://127.0.0.1:7890\nHTTPS_PROXY=http://127.0.0.1:7890"
    }
  },
  "sharedEnvironmentVariables": "HTTP_PROXY=http://127.0.0.1:7890\nHTTPS_PROXY=http://127.0.0.1:7890"
}
```

**解析逻辑**：`parseEnvironmentVariables()` 按行读 `KEY=VALUE`（支持 `export` 前缀、`#` 注释、引号），spawn 时以 `{ ...process.env, ...customEnv }` 合并，配置值会覆盖/补全缺失的代理变量。

### 4.3 P1 方案：macOS 全局环境变量

```bash
# 设置登录级全局变量（持久到重启）
launchctl setenv HTTP_PROXY http://127.0.0.1:7890
launchctl setenv HTTPS_PROXY http://127.0.0.1:7890

# 验证
launchctl getenv HTTPS_PROXY
```

### 4.4 修复效果验证

| 启动方式 | 修复前 | 修复后 |
|---------|--------|--------|
| Dock/桌面启动 | ❌ 永久卡死 | ✅ 正常 |
| 终端启动 | ✅ 正常 | ✅ 正常 |
| TUN/系统代理关闭 | ❌ 卡死 | ✅ 正常（因为显式写入了 env） |

## 5. 排查弯路与教训

### 5.1 典型误导模式

本次排查中叠加了多个无关表象，导致两次误判：

| # | 表象 | 误导方向 | 真相 |
|---|------|---------|------|
| 1 | compact 会话后开始坏 | 以为是会话内容导致的 | 时间巧合，实际是反复重启导致 env 丢失 |
| 2 | 移走爆窗会话后"恢复" | 以为是爆窗会话导致的 | 实为排查者自己的终端手动测试，不是 Claudian |
| 3 | CLI 升级后开始坏 | 以为是版本 Bug | 时间巧合，已验证新版本带代理照样正常 |
| 4 | claude.exe 文件名异常 | 怀疑是 Windows 文件 | 实为 Mach-O arm64 原生 macOS 可执行文件 |
| 5 | main.js 被注入 --print | 怀疑是探针 Bug | 是排查副作用的真 bug，但不是主因 |
| 6 | manifest.json id 冲突 | 插件加载错 | 改名无效，必须移出目录 |
| 7 | 爆窗会话 100% 占比 | 怀疑上下文超窗 | 完全无辜，可正常续接 |

### 5.2 核心教训

| 教训 | 说明 |
|------|------|
| **对照实验优先** | 环境类故障（缺环境变量、缺网络）优先用对照实验定位（有 X vs 无 X），不要被同时出现的其他异常牵着走 |
| **区分主因和副作用** | 排查用的临时探针/改动本身会制造新问题，务必与主因区分 |
| **确认"之前能用"的条件** | "之前能用现在不能用但没改配置" → 很可能是脆弱条件断裂，不是配置变更 |
| **验证"修复"的真实原因** | 排查者自己成功的测试（终端 CLI）≠ 应用自身的成功（GUI Claudian） |
| **不要假设 TUN 万能** | TUN 对本地回环和某些进程的透明代理并不可靠 |

### 5.3 排查方法论总结

```
┌──────────────────────────────────────────┐
│           环境类故障排查黄金法则            │
├──────────────────────────────────────────┤
│                                          │
│  1. 先隔离变量：有 X vs 无 X 二元对照    │
│  2. 再确认机制：ps/env/lsof 验证        │
│  3. 不被表象牵着走：区分同时出现的异常    │
│  4. 验证修复的真实原因：确保测的是目标    │
│  5. 记录过程：排查日志本身就是知识资产    │
│                                          │
└──────────────────────────────────────────┘
```

## 6. 同类故障速查

### 6.1 诊断决策树

```
"CLI/Node 工具连不上 API 但浏览器正常"
    │
    ├─ Step 1: 检查进程环境变量
    │   ps -wwE <pid> | grep proxy
    │   → 有 proxy env？
    │       ├─ ✅ 有 → 检查代理端口是否可达（curl -x http://127.0.0.1:7890 https://api.claude.ai）
    │       │           ├─ ✅ 可达 → 问题不在代理，查其他方向
    │       │           └─ ❌ 不可达 → 代理软件未启动或端口已变
    │       │
    │       └─ ❌ 无 → **确认是环境变量丢失问题**
    │           → Step 2
    │
    └─ Step 2: 检查 TCP 连接
        lsof -p <pid> -iTCP
        → 有到 API 的连接？
            ├─ ✅ 有 → 不是代理问题，查认证/限流/服务端
            └─ ❌ 无 → **确认是网络层问题，大概率是代理**
```

### 6.2 快速修复检查清单

- [ ] 代理软件是否运行中？
- [ ] 代理端口是否正确？（`netstat -an | grep 7890`）
- [ ] 目标应用是否有 proxy env？（`ps -wwE`）
- [ ] 如果没有 → 写入应用配置或 launchctl setenv
- [ ] 如果有但端口不对 → 更新 env 中的端口号
- [ ] TUN 模式 ≠ 万能 → 显式 env 更可靠
- [ ] 修复后从 Dock/桌面重启验证（不只是终端验证）

## 7. 场景脚本

### 场景一：Node.js CLI 连不上 API

**现象**：终端运行某个 Node.js CLI 工具（如 claude、npm、yarn）请求超时，但浏览器访问同一 API 正常。

**排查步骤**：
1. `echo $http_proxy $https_proxy` → 检查当前 shell 是否有代理变量
2. 有代理 → `curl -x http://127.0.0.1:7890 https://api.example.com` → 测试代理是否可达
3. 无代理 → 检查是否需要代理（直连能否访问？）
4. 需要代理 → `export HTTPS_PROXY=http://127.0.0.1:7890` → 重试 CLI
5. 如果是从 GUI 启动 → 进程没有 shell env → 需要写入应用配置或 launchctl setenv

### 场景二：GUI 应用中嵌入的 CLI 工具卡死

**现象**：如 Claudian（Obsidian 插件）中发送 prompt 后永久等待，无回复。浏览器正常。

**排查步骤**：
1. 先在终端手动跑 CLI：`claude --version` 或直接发消息 → 如果正常，问题在 GUI 启动方式
2. 检查 GUI 进程的环境变量：找到进程 PID → `ps -wwE <pid> | grep -i proxy`
3. 如果无 proxy env → **根因确认**：GUI 进程未继承代理变量
4. 修复：在应用配置中显式写入环境变量（如 Claudian 的 `claudian-settings.json`）
5. 验证：从 Dock/桌面重启应用，发消息测试

### 场景三：之前能用现在不能用但没改配置

**现象**：某个工具之前正常工作，突然不工作了，用户确认没有改动任何配置。

**排查思路**：
1. **不要往"配置变更"方向想** → 往"脆弱条件断裂"方向想
2. 可能断裂的条件：
   - 进程重启导致 env 丢失
   - 代理软件重启导致端口变化
   - 系统更新改变了网络栈行为
   - 临时文件/缓存过期
3. 对照实验验证
4. 找到断裂点后，用持久化方案替代脆弱条件

## 9. 风险提示

| 风险 | 说明 | 应对 |
|------|------|------|
| 代理端口硬编码 | 配置中写死 7890，代理软件端口变更后失配 | 修改配置中的端口号 |
| 临时探针变成新问题 | 排查中注入的代码/配置改动可能成为新故障源 | 排查结束后清理所有临时改动 |
| "恢复"的假象 | 排查者自己的测试成功 ≠ 应用本身修复 | 始终从目标应用的启动路径验证 |
| TUN 依赖 | 假设 TUN 能兜住所有流量 | 显式 env 更可靠 |
| 版本巧合 | CLI 升级时间与故障时间重合，误判为版本 Bug | 对照实验验证新旧版本 |

## 10. 知识扩展

### 10.1 各平台永久环境变量设置

| 平台 | 方法 | 影响范围 |
|------|------|---------|
| macOS | `launchctl setenv KEY VALUE` | 当前登录会话所有进程 |
| macOS | `~/.zshrc` 或 `~/.bash_profile` export | 仅终端启动的进程 |
| Windows | `setx KEY VALUE` | 后续新进程（永久） |
| Windows | 系统属性 → 高级 → 环境变量 | 全局/用户级永久 |
| Linux | `/etc/environment` | 所有进程 |
| Linux | `~/.bashrc` export | 仅终端启动的进程 |

### 10.2 Node.js 代理配置方式

| 方式 | 说明 | 推荐度 |
|------|------|--------|
| `http_proxy` env | 全局环境变量 | ⭐⭐⭐ 最通用 |
| `HTTP_PROXY` env | 大写版本（某些库优先读） | ⭐⭐⭐ 与小写同时设 |
| `global-agent` npm | 代码级全局代理 | ⭐⭐ 编程场景 |
| `proxy-agent` npm | 自动检测代理设置 | ⭐⭐ 库级 |
| `node --experimental-global-customevent` | 不适用 | ❌ |

> **Gotcha**：某些 Node.js 库只认小写 `http_proxy`，某些只认大写 `HTTP_PROXY`，某些两个都认。最安全的做法是**两个同时设置**。
