# Model Harness

> 止于知，得于行。模型是认知上限，Harness 是行动边界。
> 这个 Skill 不是教你选模型，而是帮你设计让模型稳定落地的执行框架。
>
> 与 `opc-startup` 互补：`opc-startup` 负责商业验证与资源对接，`model-harness` 负责技术执行与工程落地。

---

## 1. 任务边界

**做**
- 将模型能力封装成可重复、可监控、可迭代的 Harness
- 设计 Prompt、Tool Use、RAG、Function Calling 等执行层方案
- 建立模型评估、灰度放量、故障回退的工程链路
- 把「模型能做什么」翻译成「系统稳定产出什么」

**不做**
- 不代替用户训练/微调大模型
- 不提供模型厂商选型建议（除非涉及 Harness 适配）
- 不处理与模型执行无关的通用编码、运维、部署任务
- 不承诺“模型一定正确”；只提供降低错误率的工程手段

## 2. 核心概念速查

| 概念 | 含义 | 关键 Gotcha |
|------|------|-------------|
| Model | 预训练/微调后的神经网络权重 | 模型本身不产出业务结果，它只输出概率分布 |
| Harness | 让模型稳定落地的执行框架 | Prompt 只是 Harness 的一部分，还有路由、校验、重试、回退 |
| 止于知，得于行 | 知道模型能力上限，但价值在执行层 | 90% 的 AI 项目失败不是因为模型不够强，而是 Harness 没做好 |
| 协同进化 | Model 与 Harness 互相塑造 | 模型变强会降低 Harness 复杂度；Harness 变好会放大模型价值 |
| Prompt 工程 | Harness 的“指令层”设计 | 不是写一段话，而是设计可复用的提示模板、少样本策略、输出格式约束 |
| Tool Use | 给模型调用外部工具的能力 | 工具定义本身是 Harness 的核心资产，不是模型自带的 |
| RAG | 检索增强生成，把知识外挂 | 检索质量 > 模型能力；垃圾进，垃圾出 |
| Function Calling | 模型生成结构化调用 | 需要 Harness 做参数校验、权限检查、结果回写 |
| Guardrails | 输出校验与安全拦截 | 模型总会出错，Harness 必须拦截有害/无效输出 |
| 灰度放量 | 小范围验证 → 逐步放大 | 不要全量上线；先在 5% 流量验证，再逐步放量 |
| 故障回退 | 模型失效时的降级策略 | 必须设计“模型挂了怎么办”，不能假设模型永远可用 |
| 评估链路 | 用业务指标衡量模型效果 | 人工评分是起点，业务转化率才是终点 |

## 3. Harness 设计标准流程

### 阶段 1：任务拆解与能力映射

```
业务任务 → 子任务列表 → 每个子任务匹配模型能力 → 输出执行链路图
```

**任务拆解检查点**
- [ ] 是否能在 1 句话说清这个 Harness 要完成什么业务任务？
- [ ] 是否已识别出哪些子任务适合模型、哪些适合规则/工具？
- [ ] 是否已明确模型的“能力边界”和“失败模式”？
- [ ] 是否已设计好模型失败时的降级路径？

**能力映射原则**
- **适合模型**：需要理解、生成、分类、摘要的任务
- **适合规则**：需要精确计算、格式转换、权限校验的任务
- **适合工具**：需要访问外部数据、执行操作、调用 API 的任务

**反模式**
- 把所有子任务都塞给模型（模型会幻觉）
- 用规则硬编码所有逻辑（失去模型的灵活性）
- 忽略模型失败场景（生产环境必出问题）

### 阶段 2：Prompt 与指令设计

**Prompt 结构模板**
```
[角色定义] 你是...
[任务描述] 你的任务是...
[输入格式] 输入包含...
[输出格式] 请严格按以下格式输出...
[约束条件] 注意...
[少样本示例] 例如：
  - 输入：...
  - 输出：...
[最终指令] 现在，请处理以下输入：
```

**Prompt 工程原则**
- **明确 > 隐晦**：不要假设模型“应该知道”，明确告诉它
- **结构化 > 自由文本**：用 XML/JSON/Markdown 标签标记不同部分
- **少样本 > 长指令**：3-5 个高质量示例通常比 10 条规则更有效
- **输出约束 > 内容要求**：明确指定输出格式、长度、字段，比说“写得好”更有效

**Gotchas**
- 模型会遵循“最后的指令”，把最重要的要求放在最后
- 长 Prompt 会稀释注意力，优先保证核心指令清晰
- 温度参数（temperature）不是越高越好；精确任务用低温度（0-0.3），创意任务用高温度（0.7-1.0）

### 阶段 3：Tool Use 与 Function Calling

**工具设计原则**
- **最小权限**：工具只暴露完成任务必需的最小能力
- **幂等性**：工具应该可以安全重试，不产生副作用
- **可观测性**：每次工具调用都要记录输入、输出、耗时、状态
- **优雅降级**：工具失败时，Harness 应能继续运行或给出明确错误

**Function Calling 实现要点**
1. **工具定义**：明确定义 name、description、parameters（JSON Schema）
2. **参数校验**：Harness 必须在调用前校验参数，不依赖模型生成正确格式
3. **结果处理**：模型生成调用 → Harness 执行 → 结果回写 → 模型继续推理
4. **循环控制**：设置最大调用次数，防止无限循环

**Gotchas**
- 模型的函数调用会幻觉参数名/参数类型，Harness 必须做 schema 校验
- 工具描述影响调用成功率，描述越清晰，模型调用越准确
- 不要给模型太多工具；3-5 个精选工具 > 20 个模糊工具

### 阶段 4：RAG 与知识外挂

**RAG 链路设计**
```
用户查询 → 查询改写 → 检索 → 重排序 → 上下文构建 → 模型生成 → 答案验证
```

**各环节关键点**
- **查询改写**：把用户模糊问题转化为精确检索 query
- **检索**：向量检索 + 关键词检索混合，Top-K 不宜过大（5-20 条）
- **重排序**：用 Cross-Encoder 或规则过滤噪声，提升信噪比
- **上下文构建**：把检索结果组织成模型容易消化的格式，引用来源
- **答案验证**：检查生成答案是否基于检索内容，防止幻觉

**RAG Gotchas**
- 检索质量 > 模型能力：垃圾进，垃圾出
- 不要追求“全量知识库”；精准切片 + 高质量检索 > 海量低质数据
- 需要处理“检索不到”的情况：模型不应编造答案，而应明确告知

### 阶段 5：评估与灰度放量

**评估体系**
| 层级 | 方法 | 衡量指标 |
|------|------|----------|
| 人工评估 | 标注员评分 | 准确率、相关性、有用性 |
| 自动评估 | LLM-as-a-Judge | 与参考答案的相似度、合规性 |
| 业务评估 | A/B 测试 | 转化率、留存率、用户满意度 |
| 系统评估 | 监控看板 | 延迟、成本、错误率、回退率 |

**灰度放量流程**
1. **小流量验证**：5% 流量，人工抽检，建立基线
2. **指标监控**：实时监控延迟、错误率、业务指标
3. **自动回退**：指标异常时自动回退到旧版本或规则系统
4. **逐步放量**：5% → 20% → 50% → 100%，每阶段稳定后再推进
5. **全量观察**：全量后继续观察 7 天，确认无异常

**关键断言**
- [ ] 模型输出准确率是否达到业务要求（通常 >95%）？
- [ ] P95 延迟是否在可接受范围内（通常 <2s）？
- [ ] 错误回退率是否低于阈值（通常 <1%）？
- [ ] 业务指标是否正向（转化率、留存率等）？

### 阶段 6：故障回退与持续迭代

**故障场景与回退策略**
| 故障场景 | 回退策略 |
|----------|----------|
| 模型 API 超时/不可用 | 降级到规则系统或缓存结果 |
| 模型输出格式错误 | 解析失败时触发重试或返回默认值 |
| 模型幻觉/事实错误 | 置信度低的输出转人工审核 |
| 工具调用失败 | 记录错误，返回可解释信息，不中断流程 |
| 上下文窗口溢出 | 自动截断或摘要历史，保留关键信息 |

**持续迭代机制**
- **错误样本库**：收集模型失败的案例，定期重评估
- **Prompt 版本管理**：每个版本记录变更、效果对比、回滚方案
- **A/B 测试框架**：新 Prompt/模型/策略必须通过对比实验才能全量
- **用户反馈闭环**：建立用户反馈 → 问题定位 → Prompt 优化的闭环

## 4. 高频场景脚本

### 4.1 场景：用户想把模型能力封装成产品/服务

**执行脚本**
1. 用「任务拆解与能力映射」识别哪些环节适合模型
2. 设计 Prompt 模板 + Tool Use 方案
3. 建立评估基线：人工标注 100 条样本，计算准确率
4. 设计 Guardrails：哪些输出必须拦截、哪些必须人工审核
5. 输出最小可用 Harness，内部测试 1 周

**Gotchas**
- 不要追求“全自动”；先做“人机协作”，再逐步自动化
- 不要低估 Prompt 调试时间；通常需要 20-50 轮迭代才能稳定
- 不要把“模型能生成”等同于“系统能交付”；Harness 的职责是交付稳定结果

### 4.2 场景：用户想做 RAG 知识库问答

**执行脚本**
1. 识别知识域和问答场景（内部知识库/产品文档/客服 FAQ）
2. 设计切片策略：按段落/章节/主题切片，保留元数据
3. 选择检索方案：向量检索 + 关键词检索混合
4. 设计重排序和过滤规则
5. 建立评估集：50-100 条问答对，测试检索命中率和答案准确率
6. 上线后监控：检索无结果率、答案引用率、用户满意度

**Gotchas**
- 切片粒度影响检索效果，太大则噪声多，太小则上下文不足
- 检索结果需要“引用来源”，否则用户无法验证答案
- 必须处理“我不知道”场景；模型不应编造答案

### 4.3 场景：用户需要模型稳定执行复杂任务（Agent）

**执行脚本**
1. 拆解复杂任务为可验证的子任务
2. 为每个子任务设计 Prompt 和工具
3. 实现 ReAct 或 Plan-and-Execute 的推理框架
4. 设计状态管理：任务进度、中间结果、错误处理
5. 设置最大步数和超时，防止无限循环
6. 建立审计日志：记录每一步的输入、输出、决策

**Gotchas**
- 复杂任务的成功率随步数指数下降；10 步 Agent 成功率可能 <50%
- 必须设计“人类干预点”；完全自主 Agent 在生产环境风险极高
- 状态管理是核心难点；Harness 必须持久化任务状态，支持断点续跑

### 4.4 场景：用户需要模型输出结构化数据（Function Calling / JSON）

**执行脚本**
1. 定义 JSON Schema：明确字段名、类型、必填/可选、枚举值
2. 在 Prompt 中给出 JSON 示例和格式说明
3. Harness 层面做 schema 校验：必填字段、类型、范围
4. 设计重试策略：解析失败时，给模型明确的错误反馈和重试提示
5. 建立数据验证规则：业务逻辑校验（如日期格式、金额范围）

**Gotchas**
- 模型的 JSON 输出经常有语法错误或多余文本，必须做 robust parsing
- 不要信任模型的参数值；Harness 必须做业务层校验
- 复杂嵌套 JSON 对模型难度大，考虑分步生成或简化结构

### 4.5 场景：用户需要多模型协同（Router / Ensemble）

**执行脚本**
1. 定义路由规则：按任务类型、成本、延迟、质量要求路由到不同模型
2. 设计 fallback 链：主模型失败时自动切换到备选模型
3. 建立统一评估标准：不同模型的输出需要可比性
4. 实现成本控制：按 token 用量监控，设置预算上限
5. 输出路由日志：记录每次模型选择的原因和结果

**Gotchas**
- 模型切换会带来体验不一致；同一任务应尽量固定模型
- 便宜模型不一定“够用”；需要实际对比准确率和成本
- 路由逻辑本身是 Harness 的核心资产，需要版本管理和测试

## 6. 环境与执行约定

- 所有 Prompt 和工具定义必须版本化管理，支持回滚
- 模型输出必须经过 Harness 层校验，不直接信任模型输出
- 评估必须基于真实业务样本，不用 synthetic data 作为唯一评估标准
- 灰度放量必须设置自动回退条件，不能手动干预
- 错误样本必须进入复盘流程，转化为 Prompt 或工具优化
- 成本监控必须实时，设置预算告警阈值
- 输出结构统一为：任务拆解 → Prompt/工具设计 → 评估方案 → 灰度计划 → 故障回退 → 监控看板

## 7. 风险提示

| 风险 | 表现 | 拦截方式 |
|------|------|----------|
| Prompt 幻觉 | 模型输出格式错误、字段缺失 | Harness 层 schema 校验 + 重试 |
| 工具调用失败 | 参数错误、权限不足、服务超时 | 权限预检 + 超时控制 + fallback |
| 检索噪声 | RAG 返回无关内容 | 重排序过滤 + 引用验证 |
| 延迟爆炸 | 多轮模型调用 + 工具链过长 | 超时控制 + 缓存 + 异步处理 |
| 成本失控 | token 消耗超出预期 | 预算监控 + 模型路由 + 缓存策略 |
| 效果幻觉 | 人工测试效果好，上线后差 | 灰度放量 + 业务指标验证 |
| 安全泄露 | 敏感数据通过 Prompt/工具泄露 | 数据脱敏 + 权限隔离 + 审计日志 |
| 供应商锁定 | 深度依赖某模型 API | 抽象接口层 + 多模型备选 |

## 8. 关键参考

### Model-Harness 理念
- 《止于知，得于行：Model × Harness 的协同进化》（2026），模型与执行框架协同进化的核心框架
- Anthropic 工程实践：模型能力上限由 Harness 决定，而非模型本身

### 工程实践
- LangChain/LlamaIndex：Agent 框架参考实现
- OpenAI Function Calling：结构化输出的行业标准
- Anthropic Tool Use：工具定义与调用最佳实践
- RAG 评估框架：RAGAS、TruLens、DeepEval

### 评估与监控
- LLM-as-a-Judge：用模型评估模型
- A/B 测试框架：科学验证模型/ Prompt 效果
- 可观测性：LangSmith、Phoenix、Weights & Biases

### 与 opc-startup 的协作关系
- `opc-startup` 输出：商业验证报告、资源对接、自动化闭环设计
- `model-harness` 输入：业务任务、用户场景、性能要求
- `opc-startup` 验证“做什么”，`model-harness` 解决“怎么做稳”
