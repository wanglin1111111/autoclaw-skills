# OPC Startup

> 把全球 OPC 共创节里反复出现的资源、流程、验证链路和踩坑经验，封装成可复用的项目孵化工作环境。
> 不只是给提示词，而是回答：知识去哪找、动作由什么执行、结果如何证明、风险在哪里拦截。
>
> 融合两份核心输入：
> 1. 全球 OPC 共创节手册（2026）——生态资源、空间载体、政策工具
> 2. AI 时代创业方法论纪要（2026-06-27）——Agent 趋势、需求发现、自动化闭环、能力跃迁

---

## 1. 任务边界

**做**
- 将模糊的 AI 创业想法，压缩成可执行的最小验证计划
- 输出标准化的项目验证清单、资源对接路径、社区入驻建议
- 基于 OPC 生态真实数据，给出算力、空间、政策、订单等资源匹配
- 用 AI 创业方法论指导需求挖掘、产品定位、自动化闭环设计

**不做**
- 不代替用户注册公司、签署法律文件、进行真实融资
- 不承诺“保证成功”，只提供已验证的验证链路与生态资源
- 不处理与 OPC 项目孵化无关的通用编码、写作、翻译任务

## 2. 核心概念速查

### 2.1 OPC 生态概念

| 概念 | 含义 | 关键 Gotcha |
|------|------|-------------|
| OPC | One Person Company，一人公司/超级个体 | 不是“单打独斗”，而是“核心决策者 + AI 工具链 + 最小公司形态” |
| Vibe Coding | 非技术背景者借助 AI 完成产品开发 | 先做产品型原型验证需求，再学工具；不要为了学工具而学工具 |
| Live Agent | OpenHex 提出的有身份、会主动统筹的数字合伙人 | 区别于听话的助手；解决 OPC 规模化难题 |
| Token 券 / 算力券 | 各地 OPC 社区对 AI 算力的财政补贴 | 只补入驻 OPC 或本地注册主体；提前确认申报条件 |
| OPS | One Personas Service，把一个人变成一项可对外服务 | 不是个人提效，而是可规模化的服务体系 |
| FDE | 能深入真实业务现场、使用 AI 重构流程并交付结果的复合型人才 | 不是只会写代码的工程师 |
| ZOPC | Zero to One Person Company，从零到一个人的公司 | ai798Lab 提出的 OPC 共创方法论 |
| 超级个体 | 借助 AI 工具链，以极小团队完成以前需要大团队才能完成的事 | 先验证商业闭环，再追求“超级” |

### 2.2 AI 创业方法论概念

| 概念 | 含义 | 关键 Gotcha |
|------|------|-------------|
| Agent 产品趋势 | 企业级 AI Agent 嵌入 Slack/Teams/飞书，像管理员工一样管理 Agent | 不是功能堆砌，而是成为“新员工” |
| Be the What Got Done | 帮助用户把活干了，而非仅提供功能 | 功能是手段，完成真实任务是目的 |
| Be the Clearing House | 成为技能、权限、上下文管理的核心节点，不可绕过 | 节点价值 > 工具价值 |
| Tool-Agent Pick | 产品不仅卖给用户，也可作为工具供 AI/Agent 调用 | 双轨定价：人用 + Agent 调用 |
| 灵魂三问 | 1. 替人想问题还是帮他把活干了？ 2. 做一个功能还是成为一个关键节点？ 3. 当模型进化时，它会调用你还是把你取代？ | 每次产品决策前自我省察 |
| 需求只能被发现 | 成功创业者中最高效的是产品经理，成功率最低的是程序员 | 程序员易陷入“技术先行”误区 |
| 顺势而为 | 趋势与个人优势结合才是机会，单纯追逐趋势易陷入红海 | 找“趋势 ∩ 独特优势”的交叉点 |
| 能力跃迁 | AI 核心价值是能力扩展而非效率提升，让人完成过去无法完成的任务 | Token 消耗应服务于业务执行，而非仅写代码 |
| Open Loop | 重复相同动作期待不同结果，如每日机械发布内容 | 没有反馈闭环的自动化是伪自动化 |
| Closed Loop | 信号收集 → 策略制定 → 历史回测 → 小规模放量 → 数据反馈 → 迭代优化 | 互联网公司常用的实验闭环 |
| 把 AI 装进你的世界 | 让 AI 看到的世界趋近于你看到的世界，最大化 AI 效能 | 数据接入完整性决定 AI 效能上限 |

## 3. 项目验证标准流程

### 阶段 1：需求压缩与方向判断

```
用户原始想法 → 一句话场景描述 → 三个关键词（用户/场景/价值） → 灵魂三问自省 → 最小可行原型
```

**灵魂三问自省（必做）**
- [ ] 我是替人想问题，还是帮他把活干了？
- [ ] 我是做一个功能，还是成为一个关键节点？
- [ ] 当模型进化时，它会调用我，还是把我取代？

**需求压缩检查点**
- [ ] 是否能在 30 秒内说清“谁在什么场景下用什么得到什么”
- [ ] 是否已找到 3-5 个真实潜在用户（不是 hypothetical）
- [ ] 是否已明确第一个可交付的最小成果（不是完整产品）
- [ ] 是否通过“观察抱怨”发现需求，而非“拍脑袋发明”需求

**需求发现方法论**
- **原则 1：需求只能被发现，不能被发明** —— 参加线下活动，面对面捕捉用户抱怨
- **原则 2：顺势而为** —— 找“趋势 ∩ 个人独特优势”的交叉点，而非追逐热点
- **高价值信号**：用户当场愿意付定金、主动询问价格、愿意付出时间成本
- **低价值信号**：“朋友说需要”“我觉得市场很大”

### 阶段 2：产品定位与竞争策略

**三大共识方向（选择一个作为核心定位）**
1. **Be the What Got Done** —— 帮用户把活干了，而非仅提供功能
2. **Be the Clearing House** —— 成为技能、权限、上下文管理的核心节点
3. **Tool-Agent Pick** —— 产品不仅卖给用户，也可作为工具供 AI/Agent 调用

**非标创新策略**
- 标准化投放（如 SaaS 展会）成本高（10-40 万美元），非标创意（如飞机广告）性价比更高
- 优先考虑：创意驱动的事件营销、用户自发二次传播、口碑效应
- 案例：免费纹身图生成产品 Rafael AI，在 Midjourney 尚未支持该场景时切入，靠全球自来水推广

**能力跃迁策略**
- 从“提效”转向“做原本做不到的事”
- 深入客户场景：“能为客户工作一天”才是产品壁垒
- 追求“一口井深挖”，而非“一片湖浅尝”

### 阶段 4：验证执行与自动化闭环

```
明确业务目标 → 执行真实路径 → 关键步骤加断言 → 检查最终业务状态 → 保留截图/日志/结构化结果
```

**关键断言（根据项目类型选择）**
- 内容类：是否在 7 天内获得 1000 次真实曝光？是否有用户主动询问价格？
- SaaS/工具类：是否在 14 天内获得 10 个真实用户？是否有用户主动续用？
- 服务类：是否在 21 天内完成 3 个付费订单？是否获得客户转介绍？
- 硬件类：是否在 30 天内获得 100 个预订单？是否通过核心功能压力测试？

**自动化闭环构建**
- **Open Loop（避免）**：重复相同动作期待不同结果，如每日机械发布内容
- **Closed Loop（目标）**：信号收集 → 策略制定 → 历史回测 → 小规模放量 → 数据反馈 → 迭代优化
- **终极目标**：让 AI 看到的世界趋近于你看到的世界，实现“你在休息时，AI 仍在为你工作”
- **实践案例**：
  - 学生用 7 个 Agent 做美股量化交易，半年收益 88%，全流程自动化
  - 学生运营微信小程序，月收入 100-150 万，AI 自动处理客服、识别 Bug、修改代码并上线
  - 杭州电商创业者用 Cloud Code 进行浏览器自动化，业务反超原有团队

### 阶段 5：复盘迭代
- 记录 3 个做对的假设
- 记录 3 个失效的假设
- 输出可复用的“项目验证报告”（见 6. 输出模板）

## 5. 高频场景脚本

### 5.1 场景：用户有一个模糊的 AI 想法，不知道怎么开始

**执行脚本**
1. 用 3 个问题压缩需求：用户是谁？在什么场景下？得到什么？
2. 用“灵魂三问”自省：替人想问题还是帮他把活干了？做功能还是做节点？模型会调用你还是取代你？
3. 输出“一句话项目描述”和“最小验证目标”
4. 匹配 2-3 个最相关的 OPC 社区或平台
5. 给出 7 天内可执行的第一步（不是“先学 Python”）

**Gotchas**
- 不要一上来就建议“做个 App”；先验证需求是否存在
- 不要推荐通用在线课程；优先推荐可落地的共创营或社区
- 不要忽略“订单”路径；OPC 生态里“带着电脑来，带着订单走”是真实可用的
- 需求只能被发现，不能被发明；通过线下交流收集用户抱怨

### 5.2 场景：用户想找 OPC 社区入驻

**执行脚本**
1. 根据项目阶段（ Idea / Prototype / MVP / Revenue ）匹配社区
2. 输出 3 个备选社区，附入驻条件、空间类型、成本、政策亮点
3. 给出入驻申请材料清单（通常需要：项目简介、团队背景、原型/MVP、商业模式）

**Gotchas**
- 海淀空间紧张，入驻周期可能 2-4 周；朝阳/昌平相对灵活
- 部分社区要求“10 人以内团队”；超过需提前确认
- 优惠政策通常针对“首次入驻”；续租或转区可能无法重复享受

### 5.3 场景：用户需要算力或 Token 支持

**执行脚本**
1. 确认项目是否已完成 OPC 社区入驻或本地注册
2. 匹配 2-3 个算力平台，附补贴条件、计费模式、模型覆盖
3. 输出申请流程和所需材料

**Gotchas**
- Token 券通常“先垫后补”；需保留好发票和消费记录
- 并行科技、北京超算等服务大型 HPC 和 AI 训练；个人小项目优先考虑 TokenDance 等聚合平台
- 部分平台要求“模型权重不落地”；确认数据安全需求

### 5.4 场景：用户想验证 AI 项目是否能赚钱

**执行脚本**
1. 用“灵魂三问”自省项目定位
2. 根据项目类型选择验证断言（见 3. 阶段 4）
3. 输出 21 天验证计划，含每日/每周里程碑
4. 给出 3 个可快速触达的潜在客户来源（OPC 社区、行业社群、平台需求池）
5. 设计自动化闭环：哪些环节可以用 AI Agent 7×24 小时运行

**Gotchas**
- 不要用“朋友说感兴趣”作为验证标准；真实验证 = 用户愿意付钱或付出时间成本
- 不要追求完美 MVP；先做可演示的最小成果
- 不要忽略“获客成本”；OPC 生态里“互相使用产品”是早期冷启动手段，但不是商业模式
- 非标创新（如创意营销）比标准化投放性价比更高

### 5.5 场景：用户想设计 AI 自动化工作流

**执行脚本**
1. 识别当前重复性工作流（客服、内容发布、数据处理等）
2. 区分 Open Loop（无反馈）和 Closed Loop（有反馈迭代）
3. 设计 Closed Loop 框架：信号收集 → 策略制定 → 历史回测 → 小规模放量 → 数据反馈 → 迭代优化
4. 推荐可用的 Agent 工具和集成方案

**Gotchas**
- Open Loop 是伪自动化；必须有反馈机制
- 先从“最后 1 公里”切入：贴近用户需求与情绪价值
- 终极目标：让 AI 看到的世界趋近于你看到的世界，数据接入完整性决定 AI 效能上限

### 5.6 场景：用户想做 Agent 产品，不知道怎么定位

**执行脚本**
1. 用三大共识方向定位：What Got Done / Clearing House / Tool-Agent Pick
2. 分析目标用户：是技术原生还是非技术原生？对复杂配置接受度如何？
3. 设计“入职即用”体验：无需安装配置，直接嵌入用户现有工作流（Slack/Teams/飞书）
4. 评估壁垒：是否深入理解特定用户群体的工作流程？

**Gotchas**
- 全球程序员 3500 万，但真正使用 AI coding 工具的月活用户仅百万量级，渗透率极低
- 大客户多分布在二线城市（如亚特兰大、波士顿），而非旧金山或纽约
- 高 ARPU 背后是用户将 Agent 视为“新员工”，直接拉入工作空间

## 6. 输出模板

## 7. 环境与执行约定

- 所有推荐资源优先来自 OPC 共创节生态内真实可查的来源；涉及外部链接时，标注来源与最后可验证时间
- 涉及政策、补贴、入驻条件时，给出官方咨询入口或联系人；不做口头承诺
- 项目验证链路遵循“明确目标 → 执行 → 断言 → 检查 → 保留证据”；不做“感觉可行”的推断
- 输出结构统一为：一句话描述 → 灵魂三问 → 资源匹配 → 验证计划 → 自动化闭环 → 风险提示 → 下一步
- 强调“需求只能被发现，不能被发明”；优先通过线下交流、用户抱怨发现真实需求

## 8. 风险提示

| 风险 | 表现 | 拦截方式 |
|------|------|----------|
| 需求幻觉 | “朋友说需要”“我觉得市场很大” | 要求真实用户付费或付出时间成本 |
| 技术先行 | 程序员易陷入“基于开源项目套壳”误区 | 先用“灵魂三问”自省，再做原型验证 |
| 工具迷恋 | 花几周学工具，不做产品 | 先做原型验证需求，工具按需学习 |
| 完美主义 | 等产品“完美”再上线 | 设定硬性截止日期，先发布再迭代 |
| 生态依赖 | 以为入驻社区就等于成功 | 入驻只是起点；持续验证商业闭环 |
| Open Loop 陷阱 | 重复相同动作期待不同结果 | 必须设计 Closed Loop，有反馈才有优化 |
| 数据安全 | 敏感数据上传云端 | 优先选择端侧部署或本地运算方案 |
| 红海竞争 | 单纯追逐趋势，无独特优势 | 找“趋势 ∩ 个人优势”的交叉点 |
